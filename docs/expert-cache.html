EXL3 GPU expert cache

Full Qwen3.8 text-model generation passed on an RTX 5090. The local vLLM integration loaded all 48 decoder layers through the expert cache and used a packed PLE table in pinned host RAM. This is an eager, single-GPU smoke test; throughput, long-context behavior and broader model quality remain unqualified.

Implemented behavior

Packed expert sources remain in pinned host RAM. A device-side global LRU planner chooses GPU slots across layers, and a Triton kernel copies only missing expert rows. The EXL3 kernel receives logical-expert pointer tables updated in place on the GPU. No CPU routing readback occurs in decode. Wider batches copy a full expert layer into a separate reusable GPU buffer, leaving decode residency unchanged.

K2 and K3 layers share slots sized for the largest packed expert. Padding is unused capacity; it does not change the encoded precision or requantize any weights. N-gram embeddings and dense layers are outside this cache.

Setup and launch

This Qwen recipe targets vLLM commit e378275a8f20eac9e92212e4a1fee84ec5a31dc7. It differs from the upstream plugin's general compatibility target. The full-model run used Python 3.12.8, PyTorch 2.13.0+cu130, Triton 3.7.1, safetensors 0.8.0 and an RTX 5090. ExLlamaV3 1.5.2 native sources were rebuilt with CUDA toolkit 13.4 for SM120 against that exact PyTorch environment. A binary built for PyTorch 2.11 failed to import and cannot be reused.

Use a vLLM source checkout at the pinned commit, installed with compiled extensions matching the active PyTorch/CUDA environment. Apply the supplied three-file compatibility patch before installation. It installs the expert cache after loading, adapts Qwen PLE, and passes EXL3 configuration to the output head. The separate NVFP4 expert-pool extension is not required.

# Run from this repository, with the matching Python environment active.
export VLLM_SOURCE=/path/to/vllm-at-e378275
git -C "$VLLM_SOURCE" apply "$PWD/patches/vllm-e378275-exl3-cache.patch"
# Build/install that vLLM source with matching native extensions first.
VLLM_EXL3_NO_CUDA=1 uv pip install --no-deps -e .

The plugin uses ExLlamaV3's fused CUDA kernels for this profile. To rebuild them, provide the ExLlamaV3 1.5.2 Python package directory containing ext.py and exllamav3_ext/, with its Python dependencies available in the active environment. The helper refuses a preinstalled native binary and requires a new output directory. Its output is tied to the active PyTorch build.

python scripts/build-exllamav3.py /path/to/exllamav3 /path/to/exl3-runtime --arch 12.0
export PYTHONPATH="/path/to/exl3-runtime${PYTHONPATH:+:$PYTHONPATH}"

Prepare a new serving overlay from the existing native EXL3 checkpoint. This symlinks weights and tokenizer assets, copies the configuration and rebuilds the tensor index. The source checkpoint is preserved. An existing destination is rejected; a failed preparation leaves its partial destination for inspection.

export NATIVE_MODEL=/path/to/Qwen3.8-Flash-Next-EXL3-2.50bpw
export MODEL_OVERLAY=/path/to/Qwen3.8-Flash-Next-EXL3-cache
python tools/exl3_pack_tools/prepare_qwen_overlay.py "$NATIVE_MODEL" "$MODEL_OVERLAY"
scripts/serve-exl3.sh --check-config "$MODEL_OVERLAY"
scripts/serve-exl3.sh "$MODEL_OVERLAY"

The launcher serves qwen3.8-exl3 at http://127.0.0.1:8009/v1. It defaults to eager text-only execution, one sequence, 2,048 total context tokens, a 128-token prefill batch and 1 GiB of BF16 KV storage. It keeps 64 initial expert slots per layer and stores packed experts and PLE in pinned host memory: about 54 GiB combined, plus runtime and loading overhead. Enough free host RAM is required.

curl http://127.0.0.1:8009/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{"model":"qwen3.8-exl3","messages":[{"role":"user","content":"What is the capital of Japan?"}],"max_tokens":32}'

EXL3_PYTHON selects the Python executable; EXL3_CACHE_ROWS changes cache capacity. Trailing vLLM arguments override the script defaults, for example --port 8010. Context length includes both input and output. A client entry advertising 131,072 context tokens and 32,768 output tokens does not increase the server's context or memory budget. That larger serving profile requires separate memory sizing and validation.

Explicit API

Each expert is a dictionary of gate, up and down. Each projection contains native trellis, suh, svh and mul1 tensors. Expert IDs must match the supplied layers' routing IDs.

from vllm_exl3.expert_cache import PackedExpertLayer, Exl3ExpertCache

sources = [PackedExpertLayer.from_experts(experts) for experts in layer_experts]
cache = Exl3ExpertCache(
    sources, slots_per_layer=64, top_k=10, max_decode_tokens=4,
)
cache.attach(layers)  # the loaded EXL3 MoE modules, in source order
cache.set_promotions(False)  # profiling and graph capture
# Capture the normal apply_exl3_experts calls.
cache.set_promotions(True)   # real routing, including graph replay

Set VLLM_EXL3_MOE_KERNEL=exllamav3. The cache requires the ExLlamaV3 1.5.x 35-argument fused MoE binding and pinned_cuda_view. Calls must be serialized on one CUDA stream; keep host sources immutable. Prefill is eager-only. The current scope is whole experts on one GPU, K2/K3 mul1, uniform precision within each layer, equal expert geometry across layers, at most 64 decode routing lanes, and no expert biases. Unsupported inputs raise errors.

Attaching does not release an existing layer's resident weights or change its loader. This API alone will not make a full checkpoint fit on a 32 GB GPU. A serving integration must load expert sources directly into pinned host memory, bind the cache after loading, and control the promotion gate around warm-up/capture.

Recorded validation · 29 September 2026

Two CUDA tests passed using 16 real experts each from Qwen3.8-Flash-Next decoder layers 0 (K3) and 12 (K2), with native 2560 × 640 dimensions and top-k 10. The reference is the same EXL3 weights in GPU memory through the plugin's fused kernel. Eager output maximum absolute difference was 7.62939453125e-06. The shared test tolerance was rtol=0.02, atol=0.02.

Coverage includes frozen-gate staging, promotion, cross-layer eviction, a warm hit with zero expert copies, prefill at 32/320/2200 rows, FP16 and BF16 inputs, and changed-input/changed-routing CUDA graph replay. Prefill leaves decode ownership unchanged, and occupied GPU slots match their host sources byte-for-byte.

The test used the existing ExLlamaV3 1.5.2 / PyTorch 2.11.0 environment. The subsequent full-model test used an extension rebuilt against PyTorch 2.13.0. The standalone fixture supplies only vLLM's logging-method names; it does not mock the CUDA kernels.

VLLM_EXL3_MOE_KERNEL=exllamav3 \
EXL3_CACHE_TEST_MODEL=/path/to/Qwen3.8-Flash-Next-EXL3-2.50bpw \
PYTHONPATH=src python -m pytest tests/test_expert_cache_cuda.py -v -s

Use a Python environment with compatible PyTorch, ExLlamaV3 CUDA extension, Triton, safetensors and pytest. An unset model path skips this optional test; skips are not GPU qualification.

The repository includes a portable validation record. Raw experiment logs remain local. No serving speedup is claimed.

The host loader requires VLLM_EXL3_EXPERT_CACHE_ROWS=64, VLLM_EXL3_MOE_KERNEL=exllamav3, VLLM_EXL3_NGRAM_TABLE=pinned and --enforce-eager. It rejects unsupported geometry and incomplete loads. The local vLLM patches install the cache after loading, adapt the PLE interface and pass the quantization config to the output head. Installing this plugin alone into an unmodified vLLM checkout does not provide those hooks.

The full-model run used the local vLLM fork with these EXL3 hooks. The portable patch was subsequently checked against a clean index at the pinned vLLM revision; that minimal checkout has not had a separate full-model run.

The next performance work is full-model CUDA graph integration and matched prefill/decode measurements. The standalone graph parity test does not qualify full-model graphs.
