vllm-exl3 / Setup guide · 1 October 2026

Run Qwen EXL3 on an RTX 5090

Use vLLM 0.29.1rc1.dev423+ge378275a8, based on commit e378275a8f20eac9e92212e4a1fee84ec5a31dc7, with this branch's EXL3 cache patch. The patch connects host expert loading, Qwen PLE embeddings, output heads and decode graph capture to the plugin. Installing the plugin by itself is insufficient.

This recipe covers one GPU, text-only Qwen3.8-Flash-Next EXL3 serving with packed experts in host RAM and a GPU expert cache. Start with the small eager profile, then enable the measured decode profile after a successful response.

The commands below assemble that portable installation; they are not a claim that a clean-machine rebuild was performed for this documentation update.

2. Have the hardware and checkpoint ready

  • Linux x86_64, or WSL2 with working NVIDIA GPU access. The recorded GPU is an RTX 5090 with 32 GB VRAM.
  • Enough free host RAM for about 54 GiB of pinned expert and PLE data, plus model loading and runtime overhead. Plan for a host with substantial headroom, such as 96–128 GiB RAM; 54 GiB is not the total requirement. WSL must have access to that memory.
  • A complete local Qwen3.8-Flash-Next-EXL3-2.50bpw checkpoint with its tokenizer and configuration. The recorded pack uses K2/K3 target experts and a K3 PLE table. Other packs need separate validation.
  • Git, uv, a C++ compiler, and CUDA toolkit 13.4 available. Set CUDA_HOME to the toolkit that contains bin/nvcc. PyTorch's CUDA runtime wheel does not supply the complete compiler toolchain.
  • Disk space for the existing checkpoint, downloaded wheels, source trees and native build output. Keep the source checkpoint in place: the serving overlay links to it.

These instructions serve existing EXL3 weights. The plugin and overlay helper do not quantize a model.

3. Create an isolated workspace

Run the shell blocks in order in the same Bash session. Use a new workspace; change the paths below to suit your machine. Keep the source trees and runtime directory after installation because editable packages and symlinks refer to them.

export EXL3_WORKSPACE="$HOME/qwen-exl3-setup"
mkdir -p "$EXL3_WORKSPACE"
cd "$EXL3_WORKSPACE"
uv venv --python 3.12.8 .venv
source .venv/bin/activate

git clone --branch work/exl3-expert-cache --single-branch \
  https://github.com/hz1ulqu01gmnZH4/vllm-exl3.git
export EXL3_REPO="$EXL3_WORKSPACE/vllm-exl3"
export VLLM_SOURCE="$EXL3_WORKSPACE/vllm"
export EXL3_RUNTIME="$EXL3_WORKSPACE/exl3-runtime"

# Adjust this path to your CUDA 13.4 toolkit.
export CUDA_HOME=/opt/cuda
export PATH="$CUDA_HOME/bin:$PATH"
export MAX_JOBS=4
nvcc --version
nvidia-smi

cat > "$EXL3_WORKSPACE/runtime-constraints.txt" <<'EOF'
torch==2.13.0
triton==3.7.1
transformers==5.17.0
safetensors==0.8.0
EOF

The constraints pin the core stack; they are not a complete dependency lock. If dependency resolution fails, resolve it explicitly rather than dropping a pin or letting an installer replace PyTorch after native extensions have been built.

4. Install the patched vLLM source and matching binaries

The supplied patch changes Python code. vLLM's editable installation with precompiled binaries can therefore pair the patched source with the native wheel from the same commit. Explicitly select the recorded wheel instead of letting the installer choose a newer nightly.

git clone https://github.com/vllm-project/vllm.git "$VLLM_SOURCE"
git -C "$VLLM_SOURCE" checkout --detach e378275a8f20eac9e92212e4a1fee84ec5a31dc7
git -C "$VLLM_SOURCE" apply "$EXL3_REPO/patches/vllm-e378275-exl3-cache.patch"

export VLLM_WHEEL='https://wheels.vllm.ai/e378275a8f20eac9e92212e4a1fee84ec5a31dc7/vllm-0.29.1rc1.dev423%2Bge378275a8-cp38-abi3-manylinux_2_28_x86_64.whl'
VLLM_USE_PRECOMPILED=1 VLLM_PRECOMPILED_WHEEL_LOCATION="$VLLM_WHEEL" \
  uv pip install --editable "$VLLM_SOURCE" --torch-backend=cu130 \
  --constraint "$EXL3_WORKSPACE/runtime-constraints.txt" \
  'torch==2.13.0' 'triton==3.7.1' 'transformers==5.17.0' 'safetensors==0.8.0'

VLLM_EXL3_NO_CUDA=1 uv pip install --no-deps --editable "$EXL3_REPO"

VLLM_EXL3_NO_CUDA=1 skips the plugin's optional vllm_exl3_c build. This profile still requires CUDA and uses ExLlamaV3's compiled kernels, built in the next step. It does not require the separate NVFP4 expert-pool extension.

Apply only patches/vllm-e378275-exl3-cache.patch for this recipe. The older tools/patch_vllm_qwen4_exp/ instructions belong to other runtime recipes. A failed patch application usually means a different checkout or an already patched tree.

5. Build ExLlamaV3 against this PyTorch

Fetch the v1.5.2 sources and install their Python dependencies. Let the repository helper build the extension. Its first argument is the Python package directory inside the clone, not the clone root; its output directory must not already exist.

git clone --branch v1.5.2 --depth 1 \
  https://github.com/turboderp-org/exllamav3.git "$EXL3_WORKSPACE/exllamav3"
uv pip install --requirement "$EXL3_WORKSPACE/exllamav3/requirements.txt" \
  --constraint "$EXL3_WORKSPACE/runtime-constraints.txt" --torch-backend=cu130

python "$EXL3_REPO/scripts/build-exllamav3.py" \
  "$EXL3_WORKSPACE/exllamav3/exllamav3" "$EXL3_RUNTIME" --arch 12.0 --jobs 4
export PYTHONPATH="$EXL3_RUNTIME"
export EXL3_EXPANDABLE_SEGMENTS=0

Do not install an ExLlamaV3 binary wheel into this environment before running the helper: it refuses an existing exllamav3_ext. A binary from a different PyTorch build can fail with undefined symbols even when its ExLlamaV3 version matches. Rebuild into a new runtime directory if the PyTorch build changes.

Check imports and the active paths before loading weights:

python - <<'PY'
from importlib.metadata import version
import torch
import vllm
import vllm._C
import vllm_exl3
from glm53_exl3_plugin.exl3 import Exl3Config
from exllamav3.ext import exllamav3_ext

print("vLLM:", version("vllm"), vllm.__file__)
print("PyTorch / CUDA:", torch.__version__, torch.version.cuda)
print("GPU:", torch.cuda.get_device_name(0), torch.cuda.get_device_capability(0))
print("Plugin:", vllm_exl3.__file__)
print("ExLlamaV3 extension:", exllamav3_ext.__file__)
for name in ("triton", "transformers", "safetensors"):
    print(name, version(name))
for name in ("exl3_moe", "pinned_cuda_view", "ngram_dequant"):
    assert callable(getattr(exllamav3_ext, name, None)), name
PY

vLLM should resolve inside $VLLM_SOURCE/vllm, the plugin inside this checkout, and the extension inside the new runtime build. Editable vLLM version suffixes may differ after patching; the checked-out commit and loaded paths identify the source. Imports alone do not establish serving correctness.

6. Prepare the serving overlay

The recorded checkpoint source is r0b0tlab/Qwen3.8-Flash-Next-EXL3-2.50bpw, revision 61a1a139ef2411ed6ed5717acfaff288511a1b08. If you already have the complete checkpoint, set NATIVE_MODEL to its directory and skip the download. Otherwise, download the existing pack (about 65 GB) before preparing the overlay:

export NATIVE_MODEL="$EXL3_WORKSPACE/Qwen3.8-Flash-Next-EXL3-2.50bpw"
hf download r0b0tlab/Qwen3.8-Flash-Next-EXL3-2.50bpw \
  --revision 61a1a139ef2411ed6ed5717acfaff288511a1b08 \
  --local-dir "$NATIVE_MODEL"
# If reusing an existing checkpoint instead of the download above:
# export NATIVE_MODEL=/path/to/Qwen3.8-Flash-Next-EXL3-2.50bpw
export MODEL_OVERLAY="$EXL3_WORKSPACE/Qwen3.8-Flash-Next-EXL3-cache"
python "$EXL3_REPO/tools/exl3_pack_tools/prepare_qwen_overlay.py" \
  "$NATIVE_MODEL" "$MODEL_OVERLAY"

The helper scans the existing pack, writes the EXL3 serving configuration, rebuilds the safetensors index and links the original weights and tokenizer. It preserves the source checkpoint and rejects an existing destination. Keep the generated quantization_config.quant_method set to exl3; a conflicting checkpoint declaration can override the CLI option.

7. Resolve the configuration, then serve

On WSL2, enable vLLM's pinned-memory support in the serving shell:

# WSL2 only
export VLLM_WSL2_ENABLE_PIN_MEMORY=1
cd "$EXL3_REPO"
scripts/serve-exl3.sh --check-config "$MODEL_OVERLAY"
scripts/serve-exl3.sh "$MODEL_OVERLAY"

The first command resolves configuration without loading weights. Expect quantization: exl3, enforce_eager: true, context 2048, one sequence and 1073741824 KV bytes. The second starts the server. The initial recorded startup took about nine minutes; wait for it to report readiness before sending a request.

A successful setup returns a completion, not just a successful import or config check. The recorded eager smoke response was “The capital of Japan is Tokyo.” Stop the foreground server with Ctrl+C before changing profiles.

For subsequent sessions, reactivate $EXL3_WORKSPACE/.venv and restore CUDA_HOME, PATH, PYTHONPATH to the runtime, and your model paths. The launcher sets the EXL3 cache and PLE variables it needs. It defaults to offline Hugging Face access, so complete all downloads before launching. EXL3_PYTHON can select an explicit Python executable.

8. Optional: the measured faster decode profile

After the eager smoke test, this profile enables compact K2/K3 cache banks, cooperative kernels, decode CUDA graphs and three MTP draft tokens. It uses one active request, a resident K4 draft layer and 4.5 GiB of KV. The checkpoint must contain the MTP weights.

EXL3_CACHE_POLICY=precision-lru EXL3_CACHE_ROWS=160 \
VLLM_EXL3_COOP=1 EXL3_DECODE_GRAPHS=1 \
scripts/serve-exl3.sh "$MODEL_OVERLAY" \
  --max-model-len 131072 --max-num-seqs 1 --max-num-batched-tokens 2048 \
  --kv-cache-memory-bytes 4831838208 \
  --speculative-config '{"method":"mtp","num_speculative_tokens":3}' \
  --compilation-config '{"mode":0,"cudagraph_mode":"FULL_DECODE_ONLY","cudagraph_capture_sizes":[4]}'

The recorded comparison measured 68.74 decode tokens/s across two short prompts, using 11.15 GiB for expert banks. This is a workload result, not a guaranteed rate. Prefill remains eager. The configured 131,072-token limit does not establish full-context operation; full 131K input, 32K output and broad model quality remain unqualified.

serve-exl3-131k.sh is a separate local-workspace profile using FP8 KV, four sequences and no MTP. It expects the original workspace's supervise.py and runtime paths. Use the portable serve-exl3.sh command above for this fresh setup. Four simultaneous full-length contexts have not been validated.

See the expert-cache implementation and validation record for cache sizing, graph limits and additional performance results.

When setup fails

SymptomCheck or action
Undefined symbols in a CUDA extensionCheck the printed PyTorch version and module paths. Rebuild ExLlamaV3 in a new output directory against that PyTorch. vLLM binaries must match their source commit and PyTorch build too.
PLE rejects Exl3Config, or experts fill VRAM during loadConfirm Python imports the patched vLLM checkout and the complete cache patch is applied. The stock wheel alone lacks this integration.
ExLlamaV3 build helper refuses to runUse the package directory containing ext.py, an unused output directory and an environment without a preinstalled exllamav3_ext. Make sure nvcc comes from CUDA_HOME.
Quantization mismatch or missing tensorsPoint the launcher at the generated overlay, verify that the native checkpoint is complete, and inspect its derived EXL3 config. Do not reuse the NVFP4 checkpoint configuration.
Host allocation failure or process killed during loadingAllow more than the roughly 54 GiB pinned payload plus loading overhead. Check available memory inside WSL as well as on the host. Reducing GPU cache rows does not eliminate the pinned source weights.
CUDA OOM or KV capacity rejectionReturn to the small eager profile, free competing GPU allocations, then size cache rows and KV together. Context includes input plus output. The measured 131K MTP profile needed 4.5 GiB KV; 4 GiB was rejected.
Graph or routing-capacity error after changing concurrencyStay within the tested one-sequence profile. The cache supports at most 64 routing lanes: sequences × (1 + draft tokens) × top-k. Qwen's top-k is 10; graph size 4 matches one request with MTP3.
A client still cannot use 131K contextThe server's context and memory settings are authoritative. Increasing a client's advertised context or output limit does not resize the server.
